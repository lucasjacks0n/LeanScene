# Browser demo

A single page that runs LeanScene in the browser: drop a video on it, every frame is decoded
and labelled same / cut / fade, and the page shows a timeline of the probabilities, a
filmstrip, and one card per detected transition (last frame before, first frame after).
Nothing is uploaded; the video is processed in the tab.

| File | What it is |
|---|---|
| `index.html` | The page (no build step). Loads `model.js`, plus `onnxruntime-web` 1.20.1 and `mp4box` 0.5.2 from cdn.jsdelivr.net, so it needs an internet connection |
| `model.js` | The bundled weights as two ONNX graphs, base64 in a script file (2.1 MB). Generated by `export_onnx.py` and committed so the folder can be served as it is |
| `export_onnx.py` | Regenerates `model.js` and checks it against PyTorch |

## Run it

From the repository root:

```sh
python -m http.server -d demo 8765 --bind 127.0.0.1
```

Then open <http://127.0.0.1:8765/> and drop a video. Opening `demo/index.html` straight from
disk also works, since the model is a script file rather than something the page fetches.

| Option | Effect |
|---|---|
| `?ep=wasm` in the page URL | Force the CPU (WebAssembly) backend. Default is WebGPU when the browser has it, else WebAssembly |
| `?src=clip.mp4` | Process a file served next to the page instead of waiting for a drop |

To regenerate `model.js` (needs `pip install -e ".[export]"`; a checkpoint path exports other weights):

```sh
python demo/export_onnx.py [checkpoint.pt]
```

Reload the page without cache afterwards.

## Timeline

Under the filmstrip, a thin overview shows the whole video; the strip below it zooms and pans.

| Action | Effect |
|---|---|
| Pinch, or Ctrl/Cmd + scroll | Zoom around the pointer, down to 10 px per frame |
| Drag, or scroll sideways (Shift + scroll with a mouse wheel) | Move along the video |
| `−`, `+`, `Fit` | Zoom out, zoom in (around the playhead when it is in view), show everything |
| Press or drag on the overview | Move the zoomed view there |
| Click the strip | Jump the player to that frame |
| `◀` `▶`, or the left and right arrow keys | Jump to the previous or next transition |

While the video plays, the view turns the page when the playhead leaves it. Jumping from a
card or the player's own bar brings that spot into view.

## How it works

It mirrors `leanscene.frame_probs` and `leanscene.label_frames`:

1. `mp4box` demuxes the file and WebCodecs (`VideoDecoder`) decodes every frame, in order.
2. Each frame is resized to 100x100 on a canvas (bilinear). Sixty-four frames are drawn into
   one 800x800 atlas, kept in CPU memory, and read back together.
3. The frame network (`features` graph) runs on each batch. The 64-bin colour histogram is
   computed in the page from the pixels, not in the graph, where it is a large one-hot.
4. The temporal head (`head` graph) runs over the whole video in windows of 2,048 frames
   with 64 frames of overlap each side, which equals one pass.
5. Rule: cut >= 0.7, fade >= 0.8, fade runs closed over gaps of <= 8 frames. A cut is
   labelled on the first frame of the new shot.
6. Thumbnails are decoded on demand. The first pass records where each frame's bytes are in the
   file; when a picture nears the screen, the frames from the keyframe before it are read and
   decoded (about 15 ms each on the test clip). There is no second pass over the video.

No state is kept: nothing is written to disk and there is nothing to resume.

## What was checked

- **This export** (2026-11-17, the half-width weights): `export_onnx.py` compared the two graphs,
  assembled as the page assembles them, with PyTorch on 300 random frames. Largest probability
  difference 3.0e-7. In headless Chrome (WebGPU) the page found 72 transitions on a 5,995-frame
  720p clip, the same count as the Python package on that file. The entries below were made
  with the earlier full-width weights; speeds have not been re-measured.
- **The page**, with another seed of the same model (2026-11-15, Chrome 156, Apple M1 Pro): on
  90 s of BBC Planet Earth (2,250 frames) it found the same 16 cuts at the same frames as the
  Python pipeline. Per-frame probabilities differed by 0.005 on average and 0.05 at most, from
  the browser's decoder and resize. It ran at 370 to 1,500 frames/s on WebGPU over four runs
  (the spread is unexplained) and 101 frames/s on one WebAssembly thread (one run).
- **This page** (2026-11-16, headless Chrome, WebGPU, Apple M1 Pro, a training job running on the
  same machine): on a 720p H.264 video of 30,424 frames it ran at 1,096 frames/s, decoding
  included. On its first 5,995 frames it found 75 transitions where the Python package finds
  73; per-frame probabilities differed from the package's by 0.001 on average and 0.12 at most.
- **Readback fix** (same day): the atlas canvas is now kept in CPU memory (`willReadFrequently`)
  and batches are 64 frames. Before, the same two runs gave 310 and 374 frames/s; after, 1,096
  and 1,265. Measured apart, decode + resize + readback of 720p went from 415 to about 1,300
  frames/s; the model alone runs at over 4,000. The change moved probabilities by 0.009 at most
  and one transition out of 344 on the full video.
- **Thumbnails on demand and transition stepping** (2026-11-16, headless Chrome, 5,995-frame
  720p clip): results appear as soon as detection ends (1,156 frames/s, as before the change).
  Twelve on-demand thumbnails were compared with the same frames from a plain decode and
  matched, including the two frames either side of a cut. The buttons and arrow keys step to
  the right frames and the zoomed view follows. Not tried on a video with open GOPs, where a
  frame just after a keyframe could come out wrong, or on a full-length film.
- **Timeline zoom** (2026-11-16, headless Chrome, simulated pointer and wheel events on a
  5,995-frame clip): zooming keeps the frame under the pointer in place; scroll and drag move
  the view by the expected number of frames; a click seeks to the clicked frame; the overview,
  the buttons, following during playback and the 390 px layout work. Not tried with a real
  trackpad, in Safari (its pinch uses separate gesture events), or on touch screens, where
  pinch-zoom is not implemented.
- **Not checked**: Safari, Firefox, HEVC, videos above 720p, WebAssembly speed after the change.

## Limits

- MP4 / MOV only (what `mp4box` reads); the codec must be one the browser can decode.
- Files whose index (`moov`) is at the end are held in memory while they are read.
- Frame features are kept for the whole video: about 3.6 KB per frame (390 MB per hour at 30 fps).
- The page's resize is not OpenCV's, so probabilities differ slightly from the Python package.
- Rotation metadata and non-square pixels are ignored (frames are squashed to 100x100 either way).
